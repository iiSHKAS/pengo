# تحديثات Pengo بنسخة AppImage

[نظرة عامة](../README.ar.md) · [دليل التطوير](development.md)

يشرح هذا الدليل طريقة عمل تحديثات Pengo وتجهيز إصدارات Linux x86_64 الموقّعة
ونشرها في مستودع `iiSHKAS/pengo`.

## سلوك البرنامج

- التحديث التلقائي مفعّل افتراضيًا للإعدادات الجديدة والقديمة.
- يبدأ الفحص بعد 30 ثانية، ثم كل ست ساعات أثناء التشغيل. إعادة تفعيل الخيار توقظ الفحص.
- إشعار سطح المكتب وشريط داخل التطبيق يعرضان التنزيل والتقدم والتثبيت.
- التوقيع ورقم الإصدار الموقّع يُتحقق منهما قبل تغيير الملف.
- التنزيل من روابط إصدارات مستودع Pengo عبر HTTPS فقط؛ لا تمرر الواجهة روابط أو ملفات للتثبيت.
- يُكتب الملف الجديد في المجلد نفسه، وتُحفظ نسخة `Pengo.AppImage.previous`، ثم يُستبدل الملف ذريًا.
- يستمر البرنامج المفتوح باستخدام نسخته الحالية. يعمل التحديث في الفتح القادم أو بعد زر «إعادة التشغيل الآن».
- التعطيل يلغي الفحص/التنزيل الجاري. إذا بدأ الاستبدال فعليًا، يكتمل قبل حفظ التعطيل.
- الفحص اليدوي ينزّل ويثبّت أيضًا، ويعمل حتى لو كان التحديث التلقائي معطّلًا.
- لا تعمل التحديثات الذاتية مع `cargo run` أو التثبيت كملف تنفيذي عادي. يلزم AppImage من النوع 2، مملوك للمستخدم، وليس رابطًا رمزيًا.

إعادة التشغيل تستعمل ملف AppImage الخارجي، وتنظّف متغيرات بيئة النسخة القديمة،
وتحاول `systemd-run --user` ثم التشغيل المنفصل المباشر. تنتظر العملية الجديدة
خروج القديمة قبل تهيئة النسخة الواحدة والاختصارات.

## المفتاح الخاص بـ Pengo

تستخدم أدوات البناء المحلي المسارات التالية لحفظ مفتاح توقيع Pengo خارج المستودع:

| الملف | الغرض |
|---|---|
| `~/.config/pengo-release/updater.key` | المفتاح الخاص المشفّر |
| `~/.config/pengo-release/updater.password` | كلمة مرور المفتاح |
| `~/.config/pengo-release/updater.key.pub` | المفتاح العام |

المجلد بصلاحية `700` والملفات بصلاحية `600`. المفتاح العام فقط موجود داخل
`src-tauri/tauri.conf.json`. احتفظ بنسخة احتياطية آمنة من الملفات الثلاثة؛
الإصدارات المثبّتة تحتاج المفتاح نفسه للتحقق من التحديثات المستقبلية.
لا ترفع المفتاح الخاص أو كلمة مروره إلى Git أو ملفات Release.

## تجهيز GitHub مرة واحدة

ارفع ملفات المشروع إلى `iiSHKAS/pengo`. من Settings → Secrets and variables → Actions:

| النوع | الاسم | القيمة |
|---|---|---|
| Secret | `TAURI_SIGNING_PRIVATE_KEY` | محتوى `updater.key` |
| Secret | `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | محتوى `updater.password` |
| Variable | `TAURI_UPDATER_PUBLIC_KEY` | محتوى `updater.key.pub` |

أو بعد تثبيت GitHub CLI وتنفيذ `gh auth login`، نفّذ من مجلد المشروع:

```sh
python scripts/release/configure-github.py
```

هذا الأمر يضبط القيم في المستودع فعلًا، لكنه لا ينشر إصدارًا. يمكنك تغيير مكان
ملفات المفتاح عبر `PENGO_SIGNING_DIR`.

## نشر إصدار عبر GitHub Actions

1. وحّد رقم الإصدار في `package.json` و`package-lock.json` و`src-tauri/Cargo.toml`
   و`src-tauri/Cargo.lock` و`src-tauri/tauri.conf.json`.
2. أضف ملاحظات الإصدار تحت `## [X.Y.Z]` في `CHANGELOG.md`.
3. ارفع التغييرات، ثم ارفع وسمًا مثل `0.1.0`، أو شغّل Workflow المسمى Release
   يدويًا وأدخل رقم الإصدار الرقمي مثل `0.1.0`.
4. يبني Workflow نسخة Linux x86_64، ويختبرها، ويوقّعها مع رقم الإصدار، ويُنشئ
   Release كمسودة، ويرفع الملفات، ثم ينشرها كإصدار Latest مستقر.

الملفات الناتجة:

- `Pengo.AppImage`
- `Pengo.AppImage.sig`
- `latest.json`
- `SHA256SUMS`

عنوان الفحص هو:
`https://github.com/iiSHKAS/pengo/releases/latest/download/latest.json`

وعنوان الملف داخل البيان هو:
`https://github.com/iiSHKAS/pengo/releases/download/X.Y.Z/Pengo.AppImage`

اسم الإصدار ووسم GitHub رقميان بصيغة `X.Y.Z` دون بادئة `v` أو اسم البرنامج.

لا تغيّر اسم الملف أو تخلط توقيع إصدار بملف إصدار آخر. الإصدارات الأقدم تقبل
التحديثات ذات رقم إصدار أعلى فقط. أول Release يجهّز القناة؛ تجربة الترقية تحتاج إصدارين.

## البناء والتجهيز محليًا

يلزم Rust وNode.js 22 ومكتبات بناء Tauri و`squashfs-tools`؛ قائمة حزم Ubuntu
موجودة في `.github/workflows/release.yml`.

```sh
npm ci
python scripts/release/build-local.py
```

يقرأ الأمر المفاتيح من المجلد السابق، ويبني ويوقّع ويجهّز الملفات في
`github-files-update/` دون رفعها. ملفات الإصدار الأربعة جاهزة للرفع اليدوي إلى
GitHub Release بالوسم نفسه، مع جعله Latest وليس Pre-release. عند الرفع اليدوي
استعمل `release-notes.md` الموجود في المجلد كوصف للإصدار.

للتحقق من البصمات داخل مجلد الإصدار:

```sh
sha256sum -c SHA256SUMS
```

`npm run build:appimage` متاح للبناء المباشر عندما تكون متغيرات مفاتيح التوقيع
مضبوطة في بيئة الطرفية؛ أداة `build-local.py` تكمل أيضًا التوقيع المرتبط بالإصدار
وإعداد ملفات النشر، ولذلك هي المسار المحلي الكامل.

## الاختبارات

```sh
npm test
cargo check --locked --manifest-path src-tauri/Cargo.toml --tests
cargo test --locked --manifest-path src-tauri/Cargo.toml --lib
cargo test --locked --manifest-path scripts/release/signing/Cargo.toml
cargo test --locked --manifest-path scripts/release/checks/Cargo.toml
```

المسار الأخير يختبر كود الاستبدال ومسار AppImage نفسه دون الحاجة إلى ربط WebKit.
اختبارات الواجهة تحاكي IPC؛ اختبارات التوقيع تتحقق بمكتبة التحقق التي يستخدمها
Updater، وترفض تغيير الملف أو التعليق الموقّع أو المفتاح. اختبارات الاستبدال
تتحقق من النسخة السابقة وبقاء واصف الملف المفتوح على النسخة القديمة.

تبقى تجربة إصدارين حقيقيين من GitHub، وإعادة التشغيل على X11 وWayland، وفشل
الشبكة/امتلاء القرص/المجلد غير القابل للكتابة ضمن الاختبار اليدوي قبل النشر العام.
الاختبارات المحلية ليست إثباتًا لتشغيل GitHub Actions أو لترقية AppImage منشورة.
